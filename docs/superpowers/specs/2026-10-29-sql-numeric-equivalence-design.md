# SQL numeric result equivalence

Approved audit SQL-2 only: accept equal numeric SQL values across integer, bigint, numeric and floating result types without treating text as numeric or losing high precision. This shared grader is used by original SQL and AP2; preserve ordering, multiplicity, column-name and mutation/collateral-state semantics. No UI, new task families, schema/dependency/worker/resource/preflight/scoring changes.

For SELECT results only, use PostgreSQL result field type IDs to identify scalar numeric columns. Canonicalize decimal values as sign, significant digits and decimal scale, without coercing bigint/numeric strings through JavaScript Number. Normalize insignificant zeroes and exponent notation; retain exact distinctions beyond JS safe integer/decimal precision. Numeric NULL remains NULL; text/JSON/arrays retain existing tagged canonical encoding. Avoid JSON values impersonating an internal numeric tag by embedding distinct value-signature strings inside sorted row entries. Existing type tags for nonnumeric values remain unambiguous.

Verify with actual local PGlite, not mocked result rows. Equality cases1/1.0/1.00/exponent and inequality cases text/NULL/large adjacent integers/deep decimal differences, plus a JSON tag-shaped counterexample. Exercise both default legacy and strict AP2 caller options; retain existing ordered/unordered, duplicate, column and mutation tests. Production browser acceptance may use the guest AP2 database worker to check an equivalent numeric aggregate; no accounts, live AI or backend required.

Mutation snapshots deliberately retain the existing raw driver-value canonicalization, including numeric scale. A reference that changes only stored scale remains valid under that legacy contract; a learner end state with different scale or collateral representation changes remains different. This is separate from SELECT value equivalence, not a new mutation policy.
